## 1. Testing Overview

Testing was performed to verify the application's input validation, transaction persistence, data consistency, synthetic data generation, and automated test execution.

The project uses two testing approaches:

1. Manual application testing for transaction management and end-to-end data flow.
2. Automated synthetic data testing using Python's built-in `unittest` framework.

The automated synthetic data tests run locally and through GitHub Actions.

These two approaches serve different purposes and are documented separately.

## 3. Automated Synthetic Data Testing

### 3.1. Testing Objective

Automated tests were implemented to validate the synthetic sales data generated by Faker.

The tests focus on:

- Dataset structure and completeness.
- Unique transaction references.
- Customer and product reference consistency.
- Numeric and financial business rules.
- Transaction classification.
- Date range validation.
- Reproducible generation.
- CSV export.
- Invalid generator parameters.

### 3.2. Test Implementation

| Component         | File                                        |
| ----------------- | ------------------------------------------- |
| Data generator    | `src/generate_synthetic_data.py`            |
| Automated tests   | `tests/test_synthetic_data.py`              |
| Generated dataset | `data/synthetic/synthetic_transactions.csv` |

The generator uses Faker and Python randomization to produce synthetic customer, product, and transaction records.

Generated datasets are kept locally and excluded from Git version control.

The synthetic test workflow does not insert generated records into the production Supabase database.

### 3.3. Automated Test Cases

The test suite contains 13 test methods.

| No. | Test Method                           | Validation Objective                                              |
| --: | ------------------------------------- | ----------------------------------------------------------------- |
|   1 | `test_column_structure`               | Checks the expected CSV column structure                          |
|   2 | `test_csv_export`                     | Verifies successful CSV export                                    |
|   3 | `test_customer_reference_consistency` | Ensures customer details remain consistent for each customer code |
|   4 | `test_financial_calculations`         | Validates sales, unit profit, and total profit/loss calculations  |
|   5 | `test_invalid_generator_parameters`   | Rejects invalid row counts and date ranges                        |
|   6 | `test_no_missing_values`              | Checks for missing or empty field values                          |
|   7 | `test_numeric_business_rules`         | Validates quantity, MSRP, estimated cost, and selling price       |
|   8 | `test_order_date_range`               | Ensures generated dates are within the requested range            |
|   9 | `test_product_reference_consistency`  | Ensures product details remain consistent for each product code   |
|  10 | `test_reproducible_generation`        | Verifies deterministic generation using the same seed             |
|  11 | `test_status_and_deal_size`           | Validates Profit/Loss status and allowed deal-size values         |
|  12 | `test_transaction_count`              | Checks the requested number of transactions                       |
|  13 | `test_unique_transaction_references`  | Ensures transaction references are unique                         |

### 3.4. Running Tests Locally

Activate the project's virtual environment and run:

`python -m unittest discover -s tests -p "test_*.py" -v`

The command discovers and executes all matching test modules in the `tests/` directory.

## 4. Continuous Integration with GitHub Actions

### 4.1. Workflow Configuration

The GitHub Actions workflow is defined in:

`.github/workflows/synthetic-data-tests.yml`

The workflow uses:

- Ubuntu Latest runner.
- Python 3.11.
- Dependencies from `requirements.txt`.
- Python's built-in `unittest` framework.

### 4.2. Workflow Triggers

The workflow runs automatically on:

| Trigger         | Description                            |
| --------------- | -------------------------------------- |
| Push            | Changes pushed to the `main` branch    |
| Pull Request    | Pull requests targeting `main`         |
| Manual Dispatch | Manually triggered from GitHub Actions |

### 4.3. CI Execution Steps

The workflow performs the following steps:

1. Checks out the repository.
2. Sets up Python 3.11.
3. Installs project dependencies.
4. Executes the automated synthetic data tests.
5. Reports the workflow execution result.

The workflow uses read-only repository permissions and does not require production Supabase credentials.

## 5. Business Rules Covered by Automated Tests

The synthetic data tests validate the following project assumptions and rules.

### Quantity

- Quantity must be a positive whole number.
- Generated quantity values must be within the configured generator range.

### Pricing and Estimated Cost

- MSRP must be positive.
- Estimated cost is calculated as 50% of MSRP.
- Selling price must be greater than zero.
- Financial values are rounded to two decimal places.

### Financial Calculations

Sales:

`Selling Price × Quantity Ordered`

Profit per unit:

`Selling Price − Estimated Cost per Unit`

Total Profit/Loss:

`Profit per Unit × Quantity Ordered`

### Classification

- `Profit` is used when total profit/loss is greater than or equal to zero.
- `Loss` is used when total profit/loss is negative.
- Deal size must be one of `Small`, `Medium`, or `Large`.

These rules reflect the assumptions implemented in the synthetic data generator and the transaction application.

## 6. Test Data and Production Data Separation

The project distinguishes three data categories:

| Data Category                  | Storage / Environment   | Purpose                                         |
| ------------------------------ | ----------------------- | ----------------------------------------------- |
| Original source data           | Local `data/raw/`       | Source dataset and initial ETL                  |
| Manually entered transactions  | Supabase PostgreSQL     | Production transaction management and analytics |
| Faker-generated synthetic data | Local `data/synthetic/` | Data generation and automated testing           |

Synthetic CSV files are excluded from Git version control through `.gitignore`.

GitHub Actions executes automated data tests without connecting to the production Supabase database.

The automated workflow does not insert, update, or delete production transaction records.

## 7. Testing Scope and Limitations

The 13 automated test methods focus on the synthetic data generator and its output.

They do not represent a complete automated integration test suite for every Streamlit page, database operation, or dashboard visualization.

Transaction input, database persistence, transaction history, and dashboard refresh were verified separately through manual functional and end-to-end testing.

Additional automated integration and deployment tests may be added in future development.
